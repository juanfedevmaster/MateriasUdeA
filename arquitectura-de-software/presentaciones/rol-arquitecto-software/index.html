    Semana 4 — El Rol del Arquitecto de Software

    Apertura

    3 días

    Caso · Ficha técnica

    Netflix, agosto de 2008

    EmpresaNetflix — en 2008, todavía principalmente un servicio de alquiler de DVD por correo
    IncidenteCorrupción de la base de datos relacional central
    ImpactoNetflix no pudo enviar DVDs a sus clientes durante 3 días
    Causa raízArquitectura con un único punto de falla: toda la operación dependía de una sola base de datos centralizada
    Rol creado/asignadoCloud Systems Architect — liderado por Adrian Cockcroft desde 2007–2008
    Resultado finalMigración completa de los sistemas de streaming a AWS, con arquitectura de microservicios, anunciada terminada en 2016

    Caso ampliamente documentado en charlas públicas y publicaciones de ingeniería de Netflix (Adrian Cockcroft, "Netflix Tech Blog").

    Caso · Lo que falló

    Un solo punto, toda la operación

    La base de datos relacional que se corrompió en 2008 no era "una parte más" del sistema: era el único lugar donde vivían los datos necesarios para procesar y enviar cada pedido.

    Ningún componente podía seguir funcionando sin ella. No había redundancia, ni forma de aislar el fallo, ni un camino alterno.

    El problema no era "un bug" en ese componente — era que la arquitectura entera dependía de un único punto que podía fallar.

    Caso · El rol que se necesitó

    No un programador más — alguien que viera el sistema completo

    Resolver esto no era responsabilidad de un solo equipo arreglando su propio módulo. Se necesitaba a alguien capaz de:

    • Diagnosticar la causa estructural — no el síntoma puntual, sino la falta de redundancia en toda la arquitectura.
    • Definir principios de diseño para todos los equipos: desacoplar servicios, eliminar puntos únicos de falla, diseñar asumiendo que los componentes van a fallar.
    • Coordinar la migración entre decenas de equipos, durante años, sin detener el negocio.

    Ese conjunto de responsabilidades es, en esencia, el trabajo de un arquitecto de software — en este caso, con el título específico de Cloud Architect.

    Caso · El resultado

    De un punto único de falla a resiliencia distribuida

    La migración tomó años, no semanas. Para 2016, Netflix había trasladado por completo sus sistemas de streaming a AWS, organizados como cientos de microservicios independientes, cada uno capaz de fallar sin tumbar el sistema completo.

    Netflix incluso desarrolló herramientas para provocar fallos deliberadamente en producción (el famoso "Chaos Monkey") — una consecuencia directa de la nueva filosofía arquitectónica: si el sistema no puede sobrevivir a un fallo aislado, la arquitectura sigue estando mal.

    Transición

    ¿Quién toma decisiones de este tamaño?

    Cockcroft no escribió personalmente cada línea de los cientos de microservicios de Netflix. Su trabajo fue distinto: ver el sistema completo, definir principios, y guiar a decenas de equipos hacia una misma dirección estructural.

    Ese es exactamente el rol que estudiamos hoy: qué hace un arquitecto de software, qué tipos existen, y qué cualidades lo distinguen de otros roles técnicos.

    Concepto

    ¿Qué es un arquitecto de software?

    Un arquitecto de software es la persona (o el rol) responsable de tomar y comunicar las decisiones estructurales de un sistema — las que vimos en la Semana 3 que son costosas de revertir y afectan al sistema completo.

    No es necesariamente un título jerárquico ni el puesto de mayor antigüedad. Es, ante todo, un rol técnico: quien asume la responsabilidad de que la estructura del sistema sea coherente, sostenible y comunicable a todo el equipo.

    Concepto

    Responsabilidades típicas

    • Tomar decisiones técnicas de alto nivel: patrones arquitectónicos, tecnologías centrales, estructura de componentes.
    • Comunicar esas decisiones a stakeholders técnicos y no técnicos — desde desarrolladores hasta dirección de negocio.
    • Balancear restricciones en tensión: calidad, costo, tiempo de entrega, y los requisitos no funcionales que se estudian el jueves.
    • Guiar y mentorear a los equipos de desarrollo en la aplicación consistente de esas decisiones.
    • Revisar y ajustar la arquitectura a medida que el sistema evoluciona, sin perder de vista el conjunto.

    Concepto

    Tipos de arquitecto

    TipoAlcance de sus decisiones
    Arquitecto de Software / AplicaciónLa estructura interna de una aplicación específica
    Arquitecto de SolucionesCómo varios sistemas se integran para resolver una necesidad de negocio
    Arquitecto EmpresarialToda la cartera de sistemas de una organización, alineada a su estrategia
    Arquitecto de DatosCómo se modelan, almacenan y fluyen los datos entre sistemas
    Arquitecto de Nube (Cloud Architect)Cómo se despliega y escala el sistema en infraestructura en la nube — el rol de Cockcroft en Netflix

    Contraejemplo

    Dos mitos comunes sobre el rol

    Mito 1: "el arquitecto es quien más código escribe." El valor del rol está en las decisiones estructurales y en cómo se comunican — no en el volumen de código producido personalmente.

    Mito 2: "arquitecto es un título jerárquico, viene con antigüedad." Es un rol definido por el tipo de decisión que se toma, no por el tiempo en la empresa — alguien con pocos años de experiencia puede asumir decisiones arquitectónicas en un proyecto pequeño, como el Sprint 1 de este curso.

    Concepto

    Cualidades técnicas

    • Visión de sistemas: capacidad de ver cómo interactúan las partes, no solo cómo funciona cada una por separado.
    • Conocimiento amplio de tecnologías: no experto en todas, pero con criterio para evaluar cuándo cada una es apropiada.
    • Experiencia con las consecuencias de decisiones pasadas: haber visto qué falla y por qué, en sistemas reales.
    • Rigor con los requisitos no funcionales: escalabilidad, seguridad, mantenibilidad — se profundiza el jueves.

    Concepto

    Cualidades no técnicas

    • Comunicación clara: traducir decisiones técnicas complejas a distintas audiencias.
    • Liderazgo técnico sin autoridad formal: influir en equipos que no reportan jerárquicamente al arquitecto.
    • Capacidad de decidir bajo incertidumbre: como se vio en la Semana 3, las decisiones arquitectónicas se toman temprano, con información incompleta.
    • Mentoría: elevar el criterio técnico del equipo, no solo imponer decisiones.

    Tensión conceptual

    ¿El arquitecto debe seguir programando?

    Postura 1: un arquitecto que deja de programar pierde contacto con la realidad del código y termina tomando decisiones poco prácticas.

    Postura 2: las responsabilidades de comunicación, coordinación y visión de sistema —como las de Cockcroft durante la migración de Netflix— exigen dedicación de tiempo completo, incompatible con programar a diario.

    Síntesis

    Ideas clave de hoy

    1. Un arquitecto de software es responsable de las decisiones estructurales del sistema, no del título jerárquico ni del volumen de código escrito.
    2. Existen distintos tipos de arquitecto (software/aplicación, soluciones, empresarial, datos, nube) según el alcance de sus decisiones.
    3. Las cualidades del rol combinan lo técnico (visión de sistemas, criterio tecnológico) con lo no técnico (comunicación, liderazgo sin autoridad formal).
    4. El caso Netflix (2008–2016) muestra el rol en acción: diagnóstico estructural, decisión bajo incertidumbre, y coordinación a largo plazo.
    5. No hay consenso único sobre si un arquitecto debe seguir programando activamente — depende del contexto y la escala del sistema.

    Instrucciones · Ejemplo comentado

    De un único punto de falla a redundancia

    // ANTES: un solo repositorio, sin manejo de fallos.
// Si la fuente de datos falla, todo el sistema falla.
public class SaludoService {
    @Autowired SaludoRepository repo;
    public String generar() {
        return repo.buscarMensaje(); // sin plan B
    }
}

// DESPUÉS: decisión arquitectónica de resiliencia,
// con una fuente de respaldo ante fallo del repositorio.
public class SaludoService {
    @Autowired SaludoRepository repoPrincipal;
    @Autowired SaludoRepositoryRespaldo repoRespaldo;

    public String generar() {
        try {
            return repoPrincipal.buscarMensaje();
        } catch (Exception fallo) {
            return repoRespaldo.buscarMensaje(); // continúa operando
        }
    }
}

    No hay entregable de estudiantes: el objetivo es reconocer, a pequeña escala, la misma decisión estructural que tomó Netflix en 2008.
