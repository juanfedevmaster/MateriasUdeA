    Análisis y Diseño de Sistemas II

    Semana 4 — Interfaz Externa del Sistema: Diagramas de Secuencia del Sistema (DSS)

    Universidad de Antioquia · Ingeniería de Sistemas

    Encuadre

    Cambio de perspectiva

    Hasta ayer, el modelo describía la estructura interna del dominio: qué clases existen y cómo se relacionan. Hoy cambiamos de pregunta: ¿cómo interactúa un usuario con el sistema, visto desde afuera?

    Esta perspectiva se llama interfaz externa del sistema y se documenta con los Diagramas de Secuencia del Sistema (DSS).

    Concepto

    El sistema como caja negra

    Para diseñar la interfaz externa, el sistema completo se trata como una sola caja negra: no importa qué clases internas tiene ni cómo colaboran entre sí — solo importa qué entra (eventos del actor) y qué sale (respuestas del sistema).

    • El actor (usuario, otro sistema) envía eventos al sistema.
    • El sistema procesa internamente (eso se diseña más adelante, no hoy).
    • El sistema devuelve una respuesta observable por el actor.

    Concepto

    Evento de sistema (system event)

    Un evento de sistema es una entrada externa discreta que un actor le envía al sistema en un instante específico — típicamente la invocación de una operación.

    Se describe con una firma: nombre del evento + parámetros que lo acompañan.

    agregarProducto(idProducto, cantidad)
    confirmarPedido(idCliente)

    Concepto

    Qué es un Diagrama de Secuencia del Sistema

    Un DSS muestra, para un escenario específico de un caso de uso, la secuencia de eventos de sistema que un actor externo genera y las respuestas correspondientes — todo con el sistema representado como un único objeto :Sistema.

    • Elementos: actor (figura de palito), objeto :Sistema, líneas de vida verticales, flechas de mensaje horizontales.
    • El tiempo avanza de arriba hacia abajo.

    Concepto

    DSS y casos de uso: la misma historia, dos vistas

    Cada escenario (flujo específico, con datos concretos) de un caso de uso tiene su propio DSS. El caso de uso cuenta la historia en prosa; el DSS la traduce a eventos precisos y ordenados en el tiempo.

    Caso de uso (prosa)DSS (eventos)
    "El cliente agrega un producto al carrito"agregarProducto(idProducto, cantidad)
    "El sistema confirma que el producto fue agregado"respuesta: totalActualizado

    Concepto

    Cómo identificar eventos desde un caso de uso

    Se recorre el flujo principal del caso de uso paso a paso: cada vez que el actor hace algo que cruza la frontera hacia el sistema, hay un evento de sistema.

    Paso del caso de uso¿Es evento de sistema?
    El cliente ingresa sus datos de envíoSí — registrarDireccionEnvio(datos)
    El cliente revisa el resumen del pedidoNo — es solo lectura, no genera un evento nuevo
    El cliente confirma el pedidoSí — confirmarPedido()

    Concepto · Notación

    Mensajes, orden y retorno

    • Mensaje síncrono: flecha sólida con punta llena, del actor hacia :Sistema — el actor espera respuesta.
    • Retorno: flecha punteada, de :Sistema de vuelta al actor, con el valor o confirmación devuelta.
    • Orden temporal: los mensajes se leen estrictamente de arriba hacia abajo — el orden en el diagrama es el orden real de ocurrencia.

    Contraejemplo

    Lo que un DSS NO es

    • No es un diagrama de secuencia de diseño, con múltiples objetos internos colaborando (Controlador, Repositorio, Servicio...) — eso viene en unidades posteriores.
    • No muestra cómo el sistema procesa internamente cada evento — solo la interacción observable desde afuera.
    • No reemplaza al caso de uso — lo complementa con precisión temporal y de datos.

    Ejemplo trabajado

    DSS: "Confirmar pedido"

    Cliente                      :Sistema
      |   confirmarPedido(idCliente)   →  |
      |                                     |
      |            numeroConfirmacion    ←  -|

    El actor Cliente envía un único evento, confirmarPedido(idCliente); el sistema responde con el numeroConfirmacion generado. Todo lo que pasa dentro (validar stock, calcular total, guardar el pedido) queda oculto — es responsabilidad del diseño interno, no de este diagrama.

    Concepto

    Contrato de operación (introducción)

    Cada evento de sistema del DSS puede documentarse con un contrato de operación: un texto breve que describe precondiciones (qué debe ser cierto antes) y poscondiciones (qué cambió después) de esa operación.

    Esta semana solo se introduce el concepto — se retoma con más detalle cuando se trabaje diseño en unidades posteriores.

    Interacción · Taller

    DSS del caso de uso principal

    En equipos, sobre el caso de uso más importante de su proyecto:

    1. Identifiquen el actor principal del escenario.
    2. Listen los eventos de sistema, en orden, con su firma (nombre + parámetros).
    3. Dibujen el DSS: actor, :Sistema, mensajes y retornos.
    4. Verifiquen que ningún paso de "solo lectura" quedó convertido en evento innecesario.

    20 minutos · en salas de Zoom por equipo

    Síntesis

    Lo que hay que llevarse de hoy

    1. El sistema se trata como una caja negra al modelar su interfaz externa.
    2. Un evento de sistema es una entrada discreta del actor, con nombre y parámetros.
    3. El DSS muestra, en orden temporal, los eventos y respuestas de un escenario de caso de uso.
    4. Un DSS no es un diagrama de diseño con objetos internos — eso viene después.
    5. El contrato de operación es el siguiente nivel de detalle sobre cada evento, para unidades futuras.
