    Transición

    Tres de las cuatro vistas, con notación UML

    UML (Unified Modeling Language) es la notación gráfica estándar, mantenida por el Object Management Group (OMG), para representar la estructura de un sistema. No se ejecuta — es un lenguaje para comunicar decisiones de diseño y arquitectura entre personas.

    Hoy cubrimos tres diagramas concretos, uno por cada vista que corresponde: paquetes (lógica), componentes (desarrollo) y despliegue (física).

    Concepto · Panorama

    Qué responde cada diagrama de hoy

    DiagramaVista (4+1)Pregunta que responde
    PaquetesLógica¿Cómo se agrupan las clases del dominio en módulos?
    ComponentesDesarrollo¿Qué piezas construye el equipo y con qué interfaz se comunican?
    DespliegueFísica¿En qué hardware o infraestructura corre cada parte?

    Los tres, juntos, formalizan las capas identificadas ayer: presentación, lógica de negocio y persistencia.

    Concepto · Notación

    El diagrama de paquetes

    Un paquete se dibuja como una carpeta (rectángulo con una pestaña en la esquina superior izquierda) que agrupa un conjunto de clases relacionadas — normalmente las de una misma capa o un mismo módulo funcional.

    ┌─────────────┐
    │ Presentación├──┐
    └─────────────┘  │
                       │
    ┌─────────────┐  │
    │   Negocio    ├◁─┘

    Concepto

    Dependencias entre paquetes

    Una flecha punteada entre dos paquetes indica que el paquete de origen depende de (usa clases de) el paquete de destino.

    • Presentación depende de Negocio, y Negocio depende de Persistencia — exactamente el sentido de las capas vistas ayer.
    • Regla de buena práctica: nunca debe haber un ciclo de dependencias entre paquetes (A depende de B, B depende de A) — es la señal más clara de que las responsabilidades no están bien separadas.

    Concepto · Aplicado al proyecto

    Paquetes, sobre las capas de ayer

    PaqueteQué agrupaDepende de
    presentacionControladores, vistas, componentes de interfaznegocio
    negocioClases de dominio y servicios con las reglas de negociopersistencia
    persistenciaRepositorios y acceso a la base de datos—

    Este es el mismo mapeo de capas de la sesión de ayer, ahora expresado como estructura de paquetes de código.

    Concepto · Notación

    El diagrama de componentes

    Un componente es una pieza de software reemplazable con una interfaz bien definida. Se dibuja como un rectángulo con el estereotipo «component» (o el ícono de dos rectángulos pequeños sobresaliendo del borde izquierdo).

    ┌─────────────────────┐
    │   «component»     │
    │    ServicioPedido   │
    └─────────────────────┘

    Concepto

    Interfaz provista vs. interfaz requerida

    TipoNotaciónSignificado
    ProvistaCírculo relleno ("lollipop") unido al componenteLo que el componente ofrece a otros
    RequeridaMedia luna abierta ("socket")Lo que el componente necesita de otro para funcionar

    Dos componentes se conectan cuando el socket de uno encaja con el lollipop del otro — igual que un enchufe con su toma.

    Concepto · Ejemplo

    Dos componentes conectados

    ┌───────────────┐    ○──┐    ┌───────────────┐
    │ «component»  │         │    │ «component»  │
    │ControladorPedido├──)    ├────│ServicioPedido │
    └───────────────┘         └───────────────┘

    ControladorPedido requiere la interfaz que ServicioPedido provee — igual que ocurre en el código cuando el Controller invoca al Service.

    Concepto · Del código al diagrama

    Componentes, aplicados al proyecto

    Elemento del códigoElemento del diagrama de componentes
    PedidoControllerComponente "Controlador", expone la interfaz REST /api/pedidos
    PedidoServiceComponente "Servicio", provee la interfaz que requiere el Controlador
    PedidoRepositoryComponente "Repositorio", provee la interfaz que requiere el Servicio

    Cada flecha del diagrama corresponde exactamente a una dependencia real en el código — el diagrama no es una idealización, es un reflejo fiel de la estructura.

    Contraejemplo

    Mito: "UML es solo el diagrama de clases"

    Es común reducir UML a un único diagrama —normalmente el de clases— porque es el más enseñado. UML incluye más de una decena de tipos de diagrama, cada uno útil para una vista distinta: clases y paquetes (lógica), componentes (desarrollo), secuencia y actividad (procesos), despliegue (física).

    Usar solo el diagrama de clases para "documentar la arquitectura" es como describir un edificio solo con el plano eléctrico.

    Concepto · Notación

    El diagrama de despliegue

    Un nodo representa hardware o infraestructura de ejecución (un servidor, un dispositivo) y se dibuja como una caja en 3D (prisma). Dentro de cada nodo se colocan los artefactos desplegados en él (un archivo .jar, un contenedor).

        ╱──────────────╲
       ╱  Servidor Web  ╱│
      ╱──────────────╱ │
      │ app.jar      │╱

    Concepto

    Caminos de comunicación entre nodos

    Una línea sólida entre dos nodos representa un camino de comunicación físico o de red, normalmente etiquetado con el protocolo que usa (TCP/IP, HTTPS, JDBC).

    A diferencia del diagrama de componentes —que muestra dependencias lógicas entre piezas de software— el diagrama de despliegue muestra qué hardware necesita comunicarse con cuál, y por qué canal.

    Concepto · Aplicado al proyecto

    Despliegue típico de un proyecto de Fábrica Escuela

    NodoArtefacto desplegadoSe comunica con

    Servidor de aplicaciónapp.jar (backend Spring Boot)Servidor de base de datos, vía JDBC
    Servidor de base de datosMotor de base de datos (PostgreSQL, MySQL)—

    Concepto

    Cómo se relacionan los tres diagramas

    No son tres vistas aisladas: los paquetes agrupan las clases que implementan cada componente; los componentes, a su vez, se despliegan dentro de los nodos del diagrama de despliegue.

    Presentación (paquete) → Controlador (componente) → Servidor de aplicación (nodo): la misma pieza de software, vista desde tres ángulos distintos y con tres preguntas distintas.

    Tensión conceptual

    ¿Hay que modelar todo en UML antes de programar?

    Algunos equipos insisten en documentar exhaustivamente los tres diagramas antes de escribir una sola línea de código. Otros consideran que eso retrasa la entrega sin garantizar que el modelo sea correcto — y prefieren programar primero y diagramar solo lo esencial, después.

    Interacción

    ¿Qué diagrama responde esta pregunta?

    Para cada pregunta, identifiquen si corresponde a paquetes, componentes o despliegue:

    1. ¿Cuántos servidores necesita el sistema y cómo están conectados en red?
    2. ¿Qué módulos existen y cómo se agrupan las clases del dominio?
    3. ¿Qué componente expone la función de "registrar pedido" y con qué interfaz?
    4. ¿En qué máquina corre el motor de base de datos?

    Síntesis

    Ideas clave de hoy

    1. Los tres diagramas de hoy cubren tres de las cuatro vistas del modelo 4+1 de Kruchten (1995): paquetes (lógica), componentes (desarrollo) y despliegue (física).
    2. Paquetes: notación de carpeta, dependencias con flecha punteada, nunca deben formar ciclos.
    3. Componentes: estereotipo «component», con interfaces provistas (lollipop) y requeridas (socket) que se conectan entre sí.
    4. Despliegue: nodos en 3D con artefactos dentro, unidos por caminos de comunicación etiquetados con su protocolo.
    5. Los tres diagramas son la misma estructura de software, vista desde tres ángulos distintos — no vistas aisladas.
