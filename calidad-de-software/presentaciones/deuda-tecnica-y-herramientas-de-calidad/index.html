    Hoy: de las normas a la práctica diaria

    Las últimas cuatro semanas hablaron de normas, procesos y revisiones formales. Hoy bajamos al terreno del día a día: el código que se escribe entre una revisión y la siguiente, y cómo se degrada silenciosamente si nadie lo cuida.

    Concepto · Origen

    Qué es la deuda técnica

    El término lo acuñó Ward Cunningham en 1992 —el mismo Cunningham que años después crearía el primer wiki— como metáfora para explicarle a un cliente por qué el equipo necesitaba tiempo para reescribir código.

    La idea: escribir código rápido y no del todo limpio es como pedir un préstamo. Se puede hacer, y a veces es la decisión correcta — pero la deuda genera interés, y ese interés se paga en esfuerzo extra cada vez que alguien toca ese código después.

    Concepto

    El cuadrante de Martin Fowler

    Fowler propuso que no toda deuda técnica es un error — depende de si fue una decisión consciente y de si fue razonable tomarla:

    DeliberadaInadvertida
    Prudente"Sabemos que esto no es ideal, pero entregamos ya y lo arreglamos después.""Ahora que lo terminamos, vemos cómo debimos haberlo hecho."
    Imprudente"No tenemos tiempo para hacer las cosas bien.""¿Qué es diseño de capas?"

    La deuda prudente y deliberada, bien documentada, es una herramienta legítima — no siempre es una falla.

    Concepto

    Cómo se acumula la deuda técnica

    • Plazos apretados: se prioriza entregar sobre hacerlo bien.
    • Falta de pruebas: nadie se atreve a refactorizar sin una red de seguridad.
    • Requisitos que cambian: el diseño original ya no encaja, pero nadie lo actualiza.
    • Rotación del equipo: se pierde el contexto de por qué el código quedó así.
    • Código copiado y pegado en vez de reutilizado: el mismo defecto se multiplica.

    Concepto

    El interés de la deuda técnica

    Igual que una deuda financiera, cuanto más tiempo pasa sin pagarse, más caro sale cada cambio nuevo: hay que entender código enredado, rodear el problema en vez de resolverlo, y el riesgo de romper algo al tocarlo crece.

    La trampa común: como el interés no se ve en un balance contable, es fácil ignorarlo hasta que un cambio simple —que debería tomar una hora— termina tomando una semana.

    Transición

    Cómo se detecta la deuda técnica

    La deuda técnica no siempre se ve a simple vista en la funcionalidad —el sistema puede seguir "funcionando"—, pero sí deja señales reconocibles en la estructura del código.

    Concepto

    Qué es un code smell

    El término lo popularizaron Kent Beck y Martin Fowler en el libro "Refactoring" (1999): un "olor a código" es una señal superficial —no un error en sí mismo— que suele indicar un problema más profundo de diseño.

    • Método largo: hace demasiadas cosas para entenderlo de un vistazo.
    • Código duplicado: la misma lógica repetida en varios lugares.
    • Clase gigante: acumula responsabilidades que deberían estar separadas.
    • Lista larga de parámetros: señal de que faltan abstracciones.

    Concepto

    Qué es refactorizar

    Fowler lo define con precisión: cambiar la estructura interna de un código sin cambiar su comportamiento observable. Es la manera en que se paga la deuda técnica.

    • No es lo mismo que reescribir — reescribir empieza de cero; refactorizar transforma en pasos pequeños y verificables.
    • Necesita pruebas automatizadas que confirmen, en cada paso, que el comportamiento no cambió.
    • Se hace en pasos pequeños, no en una sola operación gigante y arriesgada.

    Concepto

    Buenas prácticas para no acumular deuda

    • Nombres significativos: una variable llamada d es deuda técnica el día en que se escribe.
    • Funciones pequeñas, una responsabilidad cada una: más fáciles de leer, probar y reutilizar.
    • No te repitas (DRY): cada pieza de lógica debería vivir en un solo lugar.
    • Comentarios solo cuando hacen falta: si el código necesita un comentario para explicarse, primero considera si se puede reescribir para que no lo necesite.

    Transición

    Cómo se mide todo esto automáticamente

    Encontrar code smells leyendo código a mano no escala a un repositorio con miles de líneas. Existe una categoría de herramientas que lo hace por nosotros: el análisis estático.

    Concepto

    Qué es el análisis estático

    Es examinar el código sin ejecutarlo —a diferencia de una prueba, que sí lo ejecuta— buscando patrones que suelen indicar bugs, vulnerabilidades o code smells. En el vocabulario de la semana 2, es una técnica de verificación: compara el código contra reglas, no contra la necesidad del usuario.

    Ya se mencionó de pasada en la semana 2 como una de las técnicas de verificación — hoy se ve en detalle, con una herramienta real.

    Concepto · Herramienta

    Qué es SonarCloud

    SonarCloud es la versión en la nube de SonarQube, la herramienta de análisis estático de SonarSource. Se conecta directamente al repositorio (GitHub, GitLab) y analiza el código en cada commit o pull request.

    Es gratuita para proyectos de código abierto — por eso es la herramienta que se usa en este curso y la que van a integrar a su pipeline de Fábrica-Escuela más adelante.

    Concepto

    Qué mide SonarCloud

    BugsCódigo que probablemente se comporta de forma distinta a la esperada
    VulnerabilidadesPuntos débiles explotables de seguridad
    Code SmellsSeñales de mantenibilidad — los mismos que vimos hace unas diapositivas
    CoberturaPorcentaje del código ejercitado por pruebas automatizadas
    DuplicaciónPorcentaje de código repetido en el proyecto
    Complejidad ciclomáticaQué tan enredado es el flujo de un método — se profundiza en la semana 11

    Concepto

    El Quality Gate

    Es un conjunto de condiciones —definidas por el equipo— que un análisis debe cumplir para considerarse aprobado: por ejemplo, "cero bugs nuevos", "cobertura mayor al 80 % en código nuevo", "cero vulnerabilidades críticas".

    Si el análisis no cumple el Quality Gate, queda en rojo — una señal visual e inmediata de que algo no está listo para fusionarse. Es la pieza que, más adelante en el curso, se conecta con el pipeline de integración continua.

    Concepto

    La severidad en SonarCloud

    SonarCloud usa su propia escala, distinta —pero comparable— a la Crítica/Alta/Media/Baja que vimos en la semana 4:

    BlockerDebe corregirse antes de continuar — riesgo muy alto de bug o vulnerabilidad
    CriticalImpacto grave en el comportamiento o la seguridad
    MajorAfecta la mantenibilidad de forma importante
    Minor / InfoMejoras menores, sin urgencia

    La herramienta asigna la severidad automáticamente — priorizar sigue siendo trabajo humano.

    Concepto

    Qué es un plan de remediación

    Encontrar un hallazgo no es suficiente: hay que decidir qué hacer con él. Un plan de remediación, por cada hallazgo priorizado, responde:

    • Qué cambio concreto corrige el problema.
    • Cuánto esfuerzo estimado toma —en horas, o en una escala relativa (pequeño/mediano/grande).
    • Cuándo se aborda — no todo se corrige de inmediato; a veces se documenta como deuda deliberada y se agenda para después.

    Ejemplo

    Un hallazgo con plan de remediación

    HallazgoMétodo procesarPago() con complejidad ciclomática de 24 (18 anidamientos de if)
    SeveridadMajor
    Por qué importaCasi imposible de probar exhaustivamente; alto riesgo al modificarlo
    RemediaciónExtraer cada rama en un método propio; considerar un patrón de estrategia
    Esfuerzo estimadoMediano (~6 horas, con pruebas de regresión antes y después)

    Interacción

    Ejercicio rápido: encuentren el code smell

    def procesar(a, b, c, d, e, f, tipo, activo, fecha, extra):
    if tipo == 1:
        if activo:
            if fecha is not None:
                # ... 40 líneas más de lógica anidada

    5 minutos: ¿qué code smell(s) identifican? ¿Cómo empezarían a refactorizarlo?

    Este ejercicio es el calentamiento del taller de hoy.

    Concepto en disputa

    ¿La herramienta reemplaza el juicio humano?

    Es tentador tratar "Quality Gate en verde" como sinónimo de "código de calidad". No lo es: SonarCloud detecta patrones, no intención — produce falsos positivos, y un código puede tener 0 % de hallazgos y aun así resolver mal el problema del usuario.

    El riesgo simétrico es "perseguir el número": subir cobertura con pruebas triviales que no verifican nada real, solo para que el porcentaje se vea bien.

    Las métricas son una brújula, no un mapa: señalan dirección, no reemplazan la revisión humana que vimos la semana pasada.

    Síntesis

    Lo que hay que llevarse de hoy

    1. La deuda técnica no siempre es un error — depende de si fue deliberada y prudente.
    2. Un code smell no es un bug: es una señal de un problema de diseño más profundo.
    3. Refactorizar cambia la estructura, no el comportamiento — y necesita pruebas para hacerse con seguridad.
    4. El análisis estático examina código sin ejecutarlo; el Quality Gate define cuándo un análisis se considera aprobado.
    5. Priorizar y estimar el esfuerzo de remediar sigue siendo trabajo humano, no algo que la herramienta decide sola.
